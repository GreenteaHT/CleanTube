# 설계 결정

큰 결정을 할 때마다 여기에 추가한다. 코드만 보고는 "왜 이렇게 했더라"를 알 수 없는 것들.
형식은 결정, 이유, 재검토 조건. 결정이 뒤집히면 지우지 말고 그 아래에 "뒤집음"과 이유를 적는다.
코드에 있다고 결정은 아니다. 실제로 고민하고 정한 것만 적는다.

## 2026-09 유튜브만, 한 단계씩

- 결정: 대상 사이트는 유튜브로 한정한다. 기능은 한 번에 하나씩, 사용자가 정한 범위만 만든다.
- 이유: 처음 뼈대에 키워드 필터, 영상 카드, 쇼츠, 흐리게 모드까지 한꺼번에 들어가 있었다. 만든 사람이 왜 있는지 모르는 기능은 배우면서 만든다는 목적에 맞지 않아서 걷어냈다. 걷어낸 코드는 첫 커밋(b30868a)에 있다.
- 재검토 조건: 없음. 다른 사이트는 유튜브가 충분히 다듬어진 뒤에나 생각한다.
- 뒤집음 (2026-10-05, "한 단계씩" 부분만): 단계를 나누지 않고 이어서 개발한다. 유튜브 한정과 "사용자가 정한 범위만"은 바꾸지 않았다.
  - 이유: 정해 둔 단계를 차례로 닫기보다 만들고 싶은 기능을 바로 이어서 만들기로 했다.

## 2026-09 1단계는 특정 작성자의 댓글 숨기기

- 결정: 첫 기능은 "@핸들 또는 채널명을 목록에 넣으면 그 사람의 댓글과 답글을 숨긴다". UI는 팝업의 목록 편집 하나.
- 이유: 사용자가 가장 먼저 원한 기능. 댓글 하나에 작성자 하나라 매칭이 단순하고, 화면에서 결과를 바로 확인할 수 있다.
- 재검토 조건: 실제 유튜브에서 확인한 뒤 매칭 규칙(정확 일치, 띄어쓰기 처리)을 확정한다.
- 뒤집음 (2026-10-05, "채널명" 부분만): 채널명으로는 매칭하지 않는다. 목록에는 @핸들 또는 채널 ID를 넣는다.
  - 이유: 댓글 응답에도 DOM에도 채널명이 없고 `@핸들`만 있다. 영상 2개의 댓글 100개에서 표시 이름이 전부 `@`로 시작했다.

## 2026-09 WXT를 쓴다

- 결정: Vite 직접 설정 대신 WXT 프레임워크.
- 이유: 비교 없이 추천으로 선택했다. `entrypoints/` 구조로 manifest를 자동 생성하고, 개발 모드에서 브라우저를 띄워 주고, storage 래퍼가 편하다는 설명을 듣고 동의했다. 지금까지 불편한 점은 없다.
- 재검토 조건: WXT 때문에 막히는 일이 생기면 CRXJS(Vite 플러그인) 등과 비교한다.

## 2026-09 DOM을 지우지 않고 속성만 토글한다

- 결정: 숨길 댓글에 `data-cleantube-blocked` 속성을 붙이고 CSS가 처리한다. `remove()`는 쓰지 않는다.
- 이유: 목록에서 빼면 되돌릴 수 있어야 한다. 유튜브 자체 스크립트가 지워진 요소를 참조하면 깨질 수 있다. 속성 값에 매칭된 항목을 넣어 두면 DevTools에서 왜 숨겨졌는지 바로 보인다.
- 부작용: 숨긴 요소도 DOM에 남는다. 아직 문제는 관찰 안 됨.
- 덧붙임 (2026-10-05): 댓글 메뉴 버튼은 유튜브 댓글 요소 안에 우리 요소를 하나 추가한다. 지우지는 않으므로 이 결정과 어긋나지 않지만, "속성만"은 더 이상 아니다.

## 2026-09 설정 상태는 storage가 단일 진실 원천

- 결정: 설정은 chrome.storage에 두고 팝업과 콘텐츠 스크립트가 각자 구독한다. 백그라운드 메모리에 상태를 두지 않고, 설정 전달에 `runtime.sendMessage`를 쓰지 않는다.
- 이유: 지금 나눌 상태가 설정 하나뿐이다. storage 변경 이벤트는 크롬이 모든 컨텍스트에 알아서 쏘므로 배달 코드가 없고, 새 탭은 storage만 읽으면 되고, 서비스 워커가 잠들어 있어도 동작한다. 그래서 백그라운드 스크립트가 없다.
- 재검토 조건: 배지 카운트나 우클릭 메뉴처럼 "상태"가 아닌 "명령"이 필요해지면 메시징을 추가한다. 그때도 설정은 storage에 남긴다. 둘은 공존한다.

## 2026-09 상태 라이브러리를 쓰지 않는다

- 결정: zustand 같은 상태 라이브러리 없이 `useSettings` 훅과 WXT storage 래퍼만 쓴다.
- 이유: 컨텍스트 간 공유는 storage가 이미 해결한다. zustand는 한 페이지 안의 상태 공유 도구라 여기에 넣으면 storage 위에 층만 하나 는다. 콘텐츠 스크립트는 React가 아니라 도움도 안 된다.
- 재검토 조건: 페이지 안에 저장하지 않는 UI 상태(검색어, 펼침 상태 등)가 많아지면 그 페이지에만 일반 zustand를 넣는다. 설정은 그대로 storage 구독. 백그라운드가 주인인 실시간 공유 상태(탭별 숨긴 개수 등)가 늘어나면 webext-zustand를 검토한다. 작은 커뮤니티 라이브러리라 그 시점의 유지보수 상태를 먼저 확인한다.

## 2026-09 storage.sync 항목 하나에 설정 전체

- 결정: `sync:settings` 키 하나에 Settings 객체를 통째로 넣는다.
- 이유: 읽기와 구독이 한 번으로 끝난다. 크롬 계정 간 동기화가 공짜다.
- 알려진 한계: sync는 항목당 8KB 제한이 있다. 목록이 수백 개가 되면 넘는다. backlog에 있음.
- 뒤집음 (2026-10-05, 차단 목록만): 차단 목록은 `local:blocked`로 옮겼다. 설정은 `sync:settings`에 남는다. 아래 "차단 목록은 storage.local에" 참고.

## 2026-09 매칭 로직은 순수 함수로 분리

- 결정: `utils/matcher.ts`는 문자열만 받고 문자열만 돌려준다. DOM, storage, WXT import 금지.
- 이유: 유튜브 DOM 없이 단위 테스트가 가능해야 한다. 대소문자, @ 처리, 띄어쓰기는 버그가 나기 쉬워서 테스트로 고정할 가치가 있다.
- 덧붙임 (2026-10-05): 이제 문자열이 아니라 `BlockEntry` 객체를 주고받고, 만료를 따지려고 현재 시각도 인자로 받는다. import 금지는 그대로다. 단위 테스트를 vitest로 넣었다(`tests/matcher.test.ts`).

## 2026-10 작성자를 채널 ID로도 식별한다

- 결정: 차단 목록 항목은 @핸들 또는 채널 ID다. 채널 ID는 페이지(MAIN) 세계 스크립트가 댓글 요소의 `commentEntity.author.channelId`를 읽어 DOM 속성으로 넘긴다.
- 이유: 핸들은 본인이 바꿀 수 있고 채널 ID는 바뀌지 않는다. 채널 ID는 HTML에 없고 유튜브가 요소에 달아 둔 JS 객체에만 있어서 페이지 세계에서 읽어야 한다. 댓글 20개의 HTML을 뒤졌을 때 채널 ID가 들어 있는 것은 0개였다.
- 대안: 댓글 응답(`/youtubei/v1/next`)을 가로채 `commentId → channelId` 표를 만드는 방법. 받기, 파싱, 저장, 댓글과 짝짓기를 우리가 해야 한다. 요소에서 읽으면 유튜브가 이미 짝지어 둔 값을 읽기만 하면 돼서 이쪽을 골랐다.
- 순서: Claude는 채널 ID를 넣어 주는 UI와 묶어 나중에 하자고 권했고, 사용자가 지금 넣기로 정했다.
- 확인한 것 (2026-10-05): 로그아웃 헤드리스 크롬과 사용자 브라우저 양쪽에서 `author.channelId`가 같은 자리에 있었다. 그 안쪽 구조(`channelCommand` 등)는 두 브라우저에서 달랐다. 요소가 DOM에 붙는 순간 값이 이미 들어 있었다.
- 알려진 한계: `commentEntity`는 유튜브 내부 이름이다. 바뀌면 채널 ID 차단만 조용히 멈추고 핸들 차단은 계속 동작한다. 패널에 "채널 ID를 못 읽음"으로 드러난다.
- 재검토 조건: `commentEntity`에서 값을 못 읽게 되면 응답 가로채기와 다시 비교한다.

## 2026-10 유튜브 화면 안에 디버그 패널

- 결정: 팝업 토글로 켜는 패널을 유튜브 화면 오른쪽에 띄운다. 확장기능이 각 댓글에서 읽은 핸들·채널 ID·매칭 결과를 보여 주고, 줄마다 차단/해제 버튼이 있다. 기본은 꺼짐.
- 이유: 사용자가 제안했다. 지금까지 확장기능이 뭘 읽었는지는 DevTools로만 볼 수 있었고, 채널 ID 차단은 DevTools에서 값을 복사해야 했다. 패널 하나로 둘 다 해결된다.
- 대안: 댓글마다 "차단" 버튼을 심는 방식. 숨긴 댓글은 `display:none`이라 그 안의 버튼으로는 해제할 수 없고, 유튜브 댓글 DOM을 댓글 수만큼 건드린다. 유튜브의 ⋮ 메뉴에 항목을 넣는 방식은 로그인해야 메뉴가 나오고 유튜브 메뉴 구조에 묶인다. 패널은 `body`에 요소 하나만 붙이고 로그인 여부와 무관하다.
- 구현 선택: Shadow DOM(유튜브 CSS와 서로 격리), React 없이 DOM API(유튜브 모든 페이지에 실리는 스크립트라 React를 넣으면 200KB 넘게 늘어남). 패널의 차단 버튼은 storage에 쓰기만 하고 화면 갱신은 기존 `watch()` 경로에 맡긴다. "설정은 storage가 단일 진실 원천" 결정을 그대로 따른 것.
- 재검토 조건: 패널에 입력창이나 필터처럼 상태가 늘어나면 React로 옮기는 것을 검토한다.

## 2026-10 최상위 댓글은 스레드째로 숨긴다

- 결정: 차단된 작성자의 댓글이 답글이면 그 답글만, 최상위 댓글이면 스레드 전체(`ytd-comment-thread-renderer`)를 숨긴다.
- 이유: 사용자가 발견했다. 댓글만 숨기면 "답글 N개" 줄이 부모 없이 남는다. 답글 묶음이 댓글 요소의 자식이 아니라 형제이기 때문이다.
- 대가: 차단한 사람의 댓글에 다른 사람이 단 답글도 같이 사라진다. 부모 없는 답글은 맥락이 없다고 보고 받아들였다.
- 재검토 조건: 남의 답글은 남기고 싶다는 요구가 생기면 "숨긴 댓글" 자리표시자를 두는 방식을 검토한다.
- 덧붙임 (2026-10-05): 이 결정은 표시 방법이 "완전히 숨기기"일 때만 해당한다. 흐리게와 "차단된 댓글"로 바꾸기는 부모가 자리에 남으므로 기본으로 답글을 둔다. 아래 "차단된 댓글의 표시 방법" 참고.

## 2026-10 사라지는 애니메이션은 사용자가 눌렀을 때만, JS로

- 결정: 차단이나 해제를 눌렀을 때만 접히고 펼쳐지는 애니메이션을 보여 준다. Web Animations API로 하고, 끝난 뒤 속성을 붙인다. 220ms는 취향값이다.
- 이유: 사용자가 원했다. CSS 트랜지션은 "속성이 바뀌었다"만 알고 "사용자가 눌러서 바뀌었다"는 모른다. CSS로 하면 스크롤로 새로 붙은, 이미 차단된 작성자의 댓글도 매번 접히는 모습이 보인다. 그 구분은 JS에서만 할 수 있다.
- 덧붙임 (2026-10-06): 흐리게와 "차단된 댓글"로 바꾸기, "숨긴 항목 보기"와 "다시 가리기"에도 넣었다. 전환마다 애니메이션을 따로 적지 않고, 속성을 바꾸기 전후의 값(요소 높이, 내용과 가림막의 자리·투명도·블러)을 재서 달라진 것만 움직인다. 자리가 바뀐 것은 transform으로 옮겨 가고 새로 보이는 것은 투명한 데서 나타난다. 끝 값을 CSS에서 읽으므로 모양은 여전히 style.css에만 있고, 설정으로 방법을 바꾸거나 열어 보는 전환도 같은 코드로 된다.
  - 바로잡음: 처음엔 차단과 해제에만 넣었다. 사용자가 실제 유튜브에서 보고 "숨긴 항목 보기"를 누를 때 블러와 "다시 가리기"가 바로 바뀐다고 해서 같은 방식으로 넣었다. 그러면서 값만이 아니라 자리도 재게 됐다. 처음엔 pill이 댓글 가운데와 맨 윗줄 사이를 옮겨 다니게 했는데 사용자가 그럴 필요 없다고 해서, 모양이 통째로 바뀌는 가림막은 옮기지 않고 새로 나타나는 것으로 본다.
  - 바로잡음: "다시 가리기"를 마우스로 누르고 커서를 치워도 가운데 pill이 계속 보였다(사용자 발견). 누른 버튼에 포커스가 남아 `:focus-within`에 걸린 것이라, 포커스로 보이는 건 키보드 포커스(`:has(:focus-visible)`)일 때만으로 좁혔다.
  - 대가: 자리표시자로 바뀔 때 내용이 먼저 사라지고 빈 자리가 줄어든다. 내용이 줄어들며 사라지게 하려면 바뀐 뒤의 높이를 미리 알아야 해서 속성을 붙였다 뗐다 해야 한다. 가려진 댓글을 완전히 숨기기로 바꾸면 접히는 동안 가림이 먼저 풀린다. 가림을 떼는 걸 접힌 뒤로 미루면 그 사이에 들어온 요청과 엉킨다. 둘 다 220ms 안의 일이라 받아들였다.
  - 확인한 것: 차단·해제는 사용자가 실제 유튜브에서 봤다. 로그아웃 헤드리스 크롬에서 차단·해제 세 방법, 열고 닫기, 설정으로 방법을 바꾸는 전환 열세 가지의 애니메이션 keyframe과 끝 상태를 봤다. 재는 스크립트는 `notes/verify-animations.mjs`.

## 2026-10 새로 붙은 댓글은 칠하기 전에 처리한다

- 결정: `MutationObserver` 콜백에서 새로 붙은 댓글은 기다리지 않고 바로 처리한다. 전체 스캔만 150ms로 묶는다.

- 확인한 것 (2026-10-05): 차단된 작성자의 댓글이 스크롤로 붙을 때, 첫 프레임 전에 숨김 속성이 붙어 있었고 보이지 않았다 (2/2). 다른 댓글은 첫 프레임에 보였다 (78/78).

  - 기본 언어(브라우저 언어가 넷 중에 없을 때)는 영어.
  - 번역은 `chrome.i18n`이 아니라 `locales/`의 TS 파일로 들고 `utils/i18n.ts`가 고른다. `chrome.i18n`은 늘 브라우저 언어를 따라서 고른 언어로 바꿀 수 없다. WXT 공식 모듈 `@wxt-dev/i18n`도 그것을 감싼 것이라 쓰지 않았다. 확장 이름과 스토어 설명만 manifest가 읽을 수 있어 `public/_locales`에 둔다.
  - 영어 파일이 기준이고 다른 언어는 `satisfies Messages`로 같은 키를 지킨다. 숫자가 들어가는 문구는 함수다(영어의 단수·복수, 언어마다 다른 어순).
  - 언어 설정(`language`)은 다른 설정처럼 `storage.sync`에 있어서 같은 크롬 계정의 다른 PC도 같은 언어가 된다. PC마다 다르게 둘 수는 없다.
  - 언어를 바꾸면 열려 있는 팝업, 설정 페이지, 유튜브 탭(가림막, 메뉴, 패널)이 다시 불러오지 않고 바로 바뀐다.
  - 첫 사용 안내의 언어 고르기는 맨 위 줄 오른쪽에 둔다. 모든 쪽에서 보인다. 예시 댓글도 언어마다 그 언어로 쓴 것을 둔다.
  - 설정 탭은 주소의 `#language`로 바로 열 수 있게 하고, 고른 탭을 주소에 적어 새로 고쳐도 그대로이게 했다.
  - 글꼴. 한글·가나·한자는 언어마다 글꼴 이름을 적은 목록을 쓴다(한국어 맑은 고딕, 일본어 Yu Gothic UI·메이리오, 중국어 Microsoft YaHei UI, 그 뒤에 macOS와 Noto). 실측에서 두 가지가 문제였다.
    - `system-ui`를 앞에 두면 한국어 윈도우에서 일본어·중국어까지 맑은 고딕으로 그리고, 맑은 고딕에 없는 글자만 다른 글꼴로 나와 한 낱말 안에서 섞였다.
    - 이름 없이 `sans-serif`와 `lang`에만 맡기면 굵기 500인 일본어의 한자(表示)만 중국어 글꼴(Microsoft YaHei)로 그렸다.
    - 번체는 Microsoft JhengHei UI, PingFang TC, Noto Sans TC.
    - 유튜브 화면에서는 우리 요소(가림막, 메뉴, 패널)에 화면 언어를 `lang`으로 단다. 유튜브 페이지의 언어와 다를 수 있다.
  - 첫 사용 안내의 쪽 넘김에서 사라지는 움직임이 끝나기를 기다리는데, 탭이 뒤로 가면 브라우저가 움직임을 멈춰 끝나지 않았다. 시간으로도 끝나게 했다.
- 확인한 것 (2026-11-15): 영어 브라우저로 띄운 로그아웃 헤드리스 크롬에서 65가지를 봤다(번체를 더한 뒤). 모두 맞았다. 안내가 영어로 열리고 다른 글자가 없는 것, 안내에서 일본어를 고르면 안내와 열려 있던 팝업이 바로 바뀌고 `<html lang>`이 바뀌는 것, 예시 댓글과 가림막도 그 언어인 것, 설정 페이지의 탭(화살표, 주소, 새로 고침), 언어 라디오, 다섯 언어 모두 팝업이 600px 안(564px)이고 칸 글이 넘치지 않는 것, 그 언어의 글꼴로 그리는 것(굵은 글 포함, `CSS.getPlatformFontsForNode`로 실제 글꼴을 읽었다), 유튜브 영상 페이지의 가림막·메뉴 버튼 이름·메뉴 항목·패널이 언어를 바꾸면 바로 바뀌는 것, 페이지 오류가 없는 것. 한국어 브라우저로는 기존 확인(팝업·차단 목록 27가지, 첫 사용 안내 63가지)이 그대로 맞았다. 스크립트는 `notes/verify-i18n.mjs`. 단위 테스트에 언어 고르기와 모든 언어의 키가 같은지를 더했다.
- 대가:
  - 일본어와 중국어(간체, 번체) 번역은 원어민 검토 전이다.
  - 문구를 더할 때마다 다섯 파일을 고쳐야 한다. 빠지면 타입 검사가 잡는다.
- 재검토 조건: 언어가 늘어 문구 관리가 번거로워지면 번역 도구를 다시 본다.

## 2026-11 차단 기능 켜기/끄기

- 결정: 팝업에서 차단 기능 전체를 켜고 끈다. 끄면 유튜브 화면에서 가림과 댓글 메뉴 버튼을 모두 떼고, 툴바 아이콘에 배지를 붙인다. 차단 목록은 그대로 두어 다시 켜면 돌아온다. 사용자가 정했다 (2026-11-15).
- 사용자가 정한 것:
  - 끄면 멈추는 범위는 가림과 메뉴 버튼 둘 다. 가림만 풀고 메뉴 버튼을 남기면 꺼진 동안에도 차단할 수 있지만, 눌러도 화면이 그대로라 헷갈린다. Claude가 둘 다를 권했다.
  - 스위치 자리는 팝업 맨 위 줄 오른쪽, "설정" 옆. 스위치만 둔다. 맨 위 줄 아래에 제목과 설명이 붙은 한 줄, 맨 아래 스위치 묶음과 견줘 골랐다. 팝업 높이가 늘지 않는다(564px 그대로).
  - 꺼져 있으면 툴바 아이콘에 배지. 꺼 둔 것을 잊으면 고장 난 것처럼 보일 수 있다고 Claude가 물었다.
- Claude가 정한 것:
  - 설정(`sync:settings`)의 `enabled`로 둔다. 다른 설정처럼 같은 계정의 다른 PC도 같이 꺼진다. PC마다 따로 둘 수는 없다.
  - 디버그 패널은 차단 기능과 상관없이 자기 스위치를 따른다. 꺼진 동안에도 패널에는 어느 댓글이 걸리는지 나온다(그 댓글은 가려지지 않은 채로).
  - 꺼도 팝업의 다른 설정은 흐리게 하지 않고 그대로 바꿀 수 있다.
  - 켜고 끌 때 가림이 풀리고 걸리는 것도 차단·해제처럼 220ms 움직인다. 사용자가 누른 변경이라서.
  - 배지 글은 화면 언어를 따른다("꺼짐", "Off", "オフ", "关闭", "關閉"). 색은 회색 바탕에 흰 글자. 꺼진 것은 뜻이 약한 색으로.
  - 스위치 이름은 "차단 기능". 맨 위 줄에는 글자가 없어서 이름과 설명은 화면 읽기 프로그램이 읽고, 이름은 마우스를 올리면 나온다.
- 확인한 것 (2026-11-15): 로그아웃 헤드리스 크롬에서 30가지를 봤다. 모두 맞았다. 팝업 맨 위 줄의 스위치(처음 켜짐, 이름과 설명, 글자가 안 보이는 것, 팝업 600px 안), 끄면 저장되고 배지 "꺼짐"이 붙는 것과 배지 색, 언어를 바꾸면 배지 글이 바뀌는 것, 다시 켜면 배지가 없어지는 것, 유튜브 영상 페이지에서 끄면 완전히 숨긴 댓글이 돌아오고 메뉴 버튼이 없어지는 것, 꺼진 동안 스크롤로 새로 붙은 댓글(20개→80개)에도 버튼이 없는 것, 다시 켜면 다시 숨기고 버튼이 붙는 것, 흐리게도 가림막까지 치우는 것, 메뉴를 연 채로 끄면 닫히는 것, 페이지 오류가 없는 것. 스크립트는 `notes/verify-enabled.mjs`.
- 대가:
  - 브라우저를 다시 켠 뒤에도 배지가 붙어 있는지는 확인하지 못했다. CDP로 올린 확장이 재시작 뒤 남지 않았다. 켤 때 워커가 돌도록 `runtime.onStartup`에 빈 리스너를 달아 두었다.
  - 툴바 아이콘으로 띄운 팝업과 배지는 사용자 크롬에서 아직 보지 않았다.

## 2026-11 배포 전 코드 리뷰에서 고친 것

첫 배포 준비에 앞서 사용자가 전체 코드 리뷰를 하자고 했다 (2026-11-15). 세 묶음(유튜브 화면의 스크립트, 저장과 동기화, 확장 페이지)으로 나눠 읽고, 지적마다 코드와 실제 유튜브에서 다시 확인한 뒤 고쳤다.

- 실측 (2026-11-15, 로그아웃 헤드리스 크롬, `notes/measure-reuse.mjs`, `notes/measure-sort-reuse.mjs`):
  - 댓글 정렬을 바꾸면(인기순↔최신순) 유튜브는 댓글 요소 20개를 그대로 두고 내용만 바꾼다. 다른 영상으로 옮기면 새 요소를 쓴다. 전에는 "요소에 적어 둔 것은 페이지를 옮기면 사라진다"고만 알고 있었다.
  - 그래서 "숨긴 항목 보기"로 열어 둔 상태가 정렬을 바꾼 뒤 그 자리에 온 다른 사람의 차단된 댓글에 남았다(셋을 열어 두면 셋 다).
  - 같은 까닭으로 정렬을 바꾼 직후 약 160ms 동안 앞 댓글의 가림이 남는다(스레드 20개 중 17개). 새로 붙은 요소가 없어서 150ms로 묶은 스캔이 맞출 때까지다. 2026-10의 스캔 실측은 스크롤로 불러오는 경우만 봤다.
  - 영상 페이지에서 홈이나 쇼츠로 가도 영상 제목 요소가 숨겨진 채 문서에 남는다.
- 사용자가 정한 것:
  - 직접 추가에 채널 주소를 붙여 넣으면 그 안의 핸들이나 채널 ID를 꺼내 넣는다. 전에는 주소가 통째로 핸들로 들어가 아무에게도 걸리지 않는 항목이 됐다. 추가를 막는 것과 견줘 골랐다.
  - 표시 방법의 움직임(접힘, 흐려짐, "숨긴 항목 보기")은 운영체제의 "동작 줄이기"를 따른다. 켜져 있으면 바로 바뀐다. 첫 사용 안내의 예시도 같은 코드라 같이 따른다.
- Claude가 정한 것 (버그 고침):
  - 기간이 끝난 임시 차단을 30일 동안 목록에 남긴다. 영구 차단을 임시로 바꾸고 기간이 끝나면, 그동안 꺼져 있던 PC가 옛 영구 차단을 모든 PC에 되살렸다. 바꿀 때는 빼기 기록이 남지 않고, 끝난 항목은 바로 버렸기 때문이다. "기간이 끝난 임시 차단은 어느 PC에서나 똑같이 끝나므로 적을 것이 없다"고 본 것이 틀렸다. 끝난 항목이 남아 있으면 더 나중에 한 그것이 옛 차단을 이긴다.
    - 끝날 때 빼기 기록을 쓰는 것도 봤다. 빼기 기록은 시각 하나라, 차단한 시각으로 적으면 기간이 30일인 차단은 쓰자마자 기록이 지워지고, 끝난 시각으로 적으면 그 사이에 다른 PC에서 건 차단까지 지운다. 항목에는 두 시각이 다 있어서 그대로 남기는 쪽이 맞다.
    - 대가: 끝난 항목이 30일 동안 sync의 자리를 쓴다. 공간이 모자랄 때 "동기화 안 됨"으로 세는 수에 끝난 항목이 섞일 수 있다.
  - 설정을 읽을 때 이 버전이 모르는 언어와 표시 방법은 기본값으로 읽는다. 나중 버전이 언어를 더하면, 아직 옛 버전인 다른 PC는 동기화로 받은 값 때문에 팝업, 설정 페이지, 유튜브 화면의 스크립트가 모두 죽는다. 쓸 때는 저장된 값 그대로에 병합해서 옛 버전이 새 버전의 값을 기본값으로 되돌리지 않게 했다.
  - 열어 둔 상태는 가린 차단 항목의 키가 달라지면 뗀다. 같은 사람의 다른 댓글이 같은 자리에 오면 열린 채로 남는다. 댓글마다 가리려면 스캔할 때마다 댓글 주소를 읽어야 해서 하지 않았다.
  - 차단한 경위의 영상 제목은 그 댓글이 들어 있는 영상 페이지에서만 찾는다.
  - 스캔과 만료의 타이머를 `ctx.setTimeout`에서 `setTimeout`으로 바꿨다. WXT의 것은 부를 때마다 정리용 리스너를 달고 떼지 않는다.
  - 직접 입력한 기간은 9999까지만 저장한다. 영어 안내의 단수형, 페이지 틀에 박혀 있던 `lang="ko"`와 한글 제목도 고쳤다.
- 확인한 것 (2026-11-15): 단위 테스트 63개. 로그아웃 헤드리스 크롬에서 정렬을 바꾼 뒤 열려 있는 댓글이 없는 것, "동작 줄이기" 9가지(`notes/verify-motion.mjs`), 기존 확인 다섯(켜기/끄기 30, 동기화 26, 디자인 31, 다국어 65, 첫 사용 안내 63)이 그대로 맞는 것.
